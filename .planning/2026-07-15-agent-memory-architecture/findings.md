# Agent Memory Architecture Findings

- The production chat path calls `LeadAgent.handle_message`, but the Lead Agent prompt currently includes only project configuration and the newest message; persisted chat history is not reloaded into model context.
- The repository contains two unused memory prototypes: `utils/agent_memory.py` and `utils/memory.py`. Neither is imported by the production Lead Agent or workflow adapter path.
- `utils/memory.py` calls its short-term memory project-level, not session-level, and its long-term SQLite design accepts `user_id` without enforcing per-user rows or database isolation.
- The current Web App presents one chat stream per project and has no multi-session/thread UI. The smallest coherent v1 therefore binds one session-memory scope to one project ID.
- Current project artifacts and `workflow_state.json` remain authoritative; Agent Memory is advisory context and must never control workflow transitions.
- OpenAI's current Agents SDK separates conversational Sessions from distilled cross-run Agent Memory. Anthropic likewise separates context compaction from persistent client-controlled memory and recommends just-in-time retrieval.
- The v1 should remain provider-neutral and use the existing LLM wrapper rather than adopting the OpenAI Agents SDK solely for memory.
- A new focused core memory service is safer than extending either unused prototype. The old prototypes should be marked legacy and left untouched during the first integration slice.
- A separate `SessionMemoryStore` and `session_state.json` existed only to support a user-facing reset lifecycle. Once Session Memory is defined as invisible Lead Agent behavior, the simplest implementation is to read the existing project transcript directly during prompt assembly.
- The former Settings design was an administrative memory console rather than a minimal product interaction. Cross-project v1 needs only an enabled boolean and clear-all operation; provenance, item metadata, diagnostics, and retrieval details remain internal.
- `LeadAgent.reply_to_project_message()` and `_schema_command()` currently build prompts without reading `chat/messages.jsonl`; both append user/assistant records only after their model call. Session integration must therefore load stored rows before the call and append the current input exactly once in the prompt.
- `WorkflowActionAdapter.run()` and every Sub Agent contract already accept `input_data`, so bounded `memory_context` can travel through the existing contract boundary without adding a new routing abstraction. Relevant contracts must explicitly preserve or consume that field because several currently rebuild their input dictionaries.
- `web_app.create_app()` owns the explicit Starlette route list and uses global `OUTPUT_ROOT` in handlers. The three Memory endpoints can follow current handler conventions and instantiate the same cross-project service directly from `OUTPUT_ROOT`.
- The current Settings row in `frontend/app.js` is static markup with no behavior. Minimal Memory UI requires a small dialog/overlay and event handlers, but no workflow-canvas changes.
- Search setup generation spreads its input config into `search_conditions.json`; injecting `memory_context` without stripping it would accidentally convert advisory memory into authoritative project state. The SearchConditionAgent must use memory in its LLM prompt but explicitly remove it from both persisted config paths.
- Extraction schema generation has a single `_schema_generation_prompt()` boundary suitable for advisory memory. Categorization suggestions similarly have one `_generate_suggestions()` prompt, while categorization application should continue using the user-confirmed current category plan.
- `categorization_mapping.json` already contains exactly the reusable `field`, `mode`, `categories`, and `category_descriptions` needed for safe promotion; row-level mapping and timestamps must be excluded.
- Frontend UI state already uses `state.dialog` and a single delegated `[data-act]` click handler. Memory can fit without a new state subsystem by adding `memoryEnabled`, `memoryPending`, `dialog === 'memory'`, one renderer, and three small fetch operations.
- The static Settings row lacks `data-act`; converting it to a button with `data-act="open-memory"` is the only sidebar change. Existing overlay/dialog styling can be reused inline, preserving the current layout and avoiding new CSS files.
